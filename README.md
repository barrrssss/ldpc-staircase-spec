# ldpc-staircase-spec

Canonical specification and conformance test vectors for **ldpc-staircase** — a
systematic, fixed-rate LDPC-Staircase erasure code over GF(2), following the RFC 5170
section 6 core constrained to the profile defined in [`SPEC.md`](SPEC.md). Given `K`
source symbols it produces `R` repair symbols by sparse XOR, and a decoder reconstructs
the source from `K + D` received symbols.

- [`SPEC.md`](SPEC.md) — the normative math/format specification.
- [`vectors/`](vectors/) — conformance test vectors (raw `*.bin` + `MANIFEST.json`),
  generated by `ldpc-staircase-java` and verified byte-for-byte by every
  implementation.
- [`reference/`](reference/) — an independent, dependency-free Python checker that
  verifies the vectors directly from `SPEC.md`, plus its differential corpus.
- [`VERSION`](VERSION) — the current normative specification version.
- [`HISTORY.md`](HISTORY.md) — protocol and implementation release history.
- [`docs/decisions/`](docs/decisions/) — shared engineering decisions that affect
  interoperable implementations.

## Not an MDS code

Unlike `erasure16-spec`'s Reed-Solomon code, this one carries **no "any `K` of
`K + R`" guarantee**. It trades that for sparse XOR encoding and normally cheap,
low-memory recovery. The symbols actually needed are `K + D`, where `D` depends on the
graph, the seed, the decoder, and heavily on the *shape* of the loss. Consumers must
read completion from the decoder's result, never from a received-symbol count.
SPEC.md section 6.3 states this normatively.

## Implementations

Each implementation consumes this repo as a git submodule at
`external/ldpc-staircase-spec` and asserts byte-exact conformance against `vectors/`:

- **ldpc-staircase-java** — Java 11; also the vector generator.
- **ldpc-staircase-dotnet** — C# / .NET (`netstandard2.0`).

The vectors have a single generator on purpose. Java writes them, both
implementations verify them, and regenerating is a specification change rather than a
routine step.

## Independent verification

A single generator keeps the byte-level oracle unambiguous, but it leaves one failure
mode open: the generator and both implementations could share one misreading of
`SPEC.md`. [`reference/`](reference/) closes that gap with a small Python checker
derived from this document rather than from either implementation, using only the
standard library. It decides recoverability by reducing the whole parity-check system
over GF(2) to reduced row echelon form instead of reproducing the profile's
peeling-plus-residual control flow, so it reaches the same answers by different means.

The release-gate command is:

```sh
python reference/ldpc_staircase_reference.py check-vectors vectors/MANIFEST.json
```

Both implementations additionally compare their results for the committed differential
corpus in [`reference/corpus.json`](reference/corpus.json) against the checker's own.
See [`reference/README.md`](reference/README.md) for the commands, the corpus payload
rule, and the independence record.

## Vector families

`vectors/MANIFEST.json` indexes five kinds used to validate byte-exact conformance:

| Section | Covers |
| --- | --- |
| `prngRaw` | the Park–Miller stream at listed ordinals, including RFC 5170's own `seed = 1` / 10,000th value criterion |
| `prngBounded` | the IEEE 754 scaling into `[0, maxv)` |
| `matrix` | parity check matrix construction, as the canonical serialization of SPEC.md section 7.1 |
| `encode` | repair symbol generation |
| `decode` | recovery: peeling-only, residual-solve, and expected-failure outcomes |

Symbol payloads are stored one blob per part, holding that part's symbols
concatenated in ascending ESI order at the case's fixed symbol length. Every blob is
listed with its byte length and SHA-256.
